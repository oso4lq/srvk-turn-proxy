# Расширение функционала vk-turn-proxy

## Общая концепция

Форк от [cacggghp/vk-turn-proxy](https://github.com/cacggghp/vk-turn-proxy).

Новый функционал управляется переменной окружения `STEALTH_MODE` (boolean):
- `false` — трафик идёт по дефолтному функционалу (обратная совместимость)
- `true` — включается весь описанный ниже STEALTH_MODE с качественной мимикрией под реальный VK-звонок

Все механизмы STEALTH_MODE встраиваются **поверх существующего DTLS-слоя**, не затрагивая его. Архитектурный стек:

```
[WireGuard UDP пакет]
        ↓
[STEALTH layer: padding + pacing + dummy]   ← новый слой
        ↓
[DTLS — существующий слой обфускации]
        ↓
[TURN / VK инфраструктура]
```

Клиент и сервер должны понимать протокол друг друга в STEALTH_MODE. Версия протокола передаётся в рукопожатии с первого коммита, чтобы обеспечить совместимость при будущих обновлениях.

---

## Wire-формат пакета в STEALTH_MODE

Все пакеты в STEALTH_MODE имеют единый заголовок:

```
[1 byte: flags] [2 bytes: original_payload_len] [payload] [random padding до target_size]
```

- `flags` — тип пакета: `0x01` data, `0x02` dummy, `0x03` keepalive
- `original_payload_len` — длина реальных данных; `0` означает dummy-пакет
- `padding` — случайные байты до нужного размера

Сервер при получении читает `original_payload_len`, отрезает паддинг и отдаёт оригинальный пакет дальше. Реализуется как изолированный пакет `stealth/`, тестируемый без поднятия TURN.

## 1. Padding

### Зачем
DPI-системы анализируют размеры пакетов и строят по ним профили приложений. Постоянный размер пакетов VPN — узнаваемая сигнатура. В реальном VK-звонке размеры аудио/видеофреймов варьируются в предсказуемом диапазоне — нужно имитировать именно это.

### Как работает
- Каждый пакет дополняется до одного из нескольких «типичных» размеров, имитирующих аудио- или видеофреймы WebRTC.
- Целевые размеры выбираются **не статично**, а с небольшим случайным шумом (±несколько байт): реальные WebRTC-фреймы тоже не бывают ровно одного размера. Статичный набор «всегда 1200 байт» сам по себе стал бы сигнатурой.
- Типичные диапазоны:
  - Аудио (Opus): 20–80 байт полезной нагрузки → целевой размер пакета ~100–200 байт
  - Видео (VP8/VP9/H.264): 500–1400 байт → целевой размер пакета ~800–1400 байт
- Сервер читает `original_payload_len` из заголовка и отбрасывает паддинг перед передачей дальше.

## 2. Pacing (ритмичная отправка)

### Зачем
Обычный VPN отправляет пакеты нерегулярно — «когда есть данные». Реальный VK-звонок шлёт пакеты с почти постоянным интервалом: аудиокодек тикает каждые 20 мс, видео — каждые ~33 мс. Нерегулярный поток выдаёт VPN даже при правильных размерах пакетов.

### Как работает
- Клиент и сервер отправляют пакеты по таймеру: **~20 мс** (имитация аудио-режима) или **~33 мс** (имитация видео-режима). Режим настраивается через параметр.
- Таймер **независим** на клиенте и сервере — не синхронизирован. У реальных собеседников в звонке часы не совпадают, синхронизированный поток выглядел бы неестественно.
- Если в текущем слоте есть реальные данные — отправляется data-пакет с паддингом.
- Если данных нет — отправляется dummy-пакет (см. раздел 3).
- Если данных больше, чем влезает в один пакет — буферизация и отправка в следующем слоте.
- При использовании нескольких каналов (`-n`) данные распределяются по каналам методом round-robin или по заполненности буфера. При n=16 и pacing 20 мс суммарная пропускная способность составляет ~8.96 Мбит/с — приемлемо для бытового VPN.

## 3. Dummy traffic в idle

### Зачем
Когда пользователь ничего не делает, обычный VPN-туннель молчит — это легко детектируется как «не звонок». Реальные аудиокодеки (Opus) продолжают слать пакеты даже в тишине: так называемые **comfort noise (CN) пакеты**. Молчащий туннель — явный признак не-звонка.

### Как работает
- Когда реальных данных нет, в каждом pacing-слоте отправляется dummy-пакет.
- Dummy-пакет имитирует comfort noise: маленький (~10–80 байт полезной нагрузки), дополненный паддингом до размера аудиофрейма.
- `flags = 0x02` (dummy), `original_payload_len = 0` — сервер распознаёт и отбрасывает такой пакет, не передавая его дальше в туннель.
- Туннель никогда полностью не молчит, пока соединение активно.

## 4. DTLS Fingerprinting

### Зачем
DTLS-рукопожатие имеет узнаваемый fingerprint. Если форк изменит параметры DTLS (cipher suites, extensions, порядок), это создаст новую сигнатуру — уже не VK-звонка, но и не настоящего DTLS. Важно не сломать то, что уже работает.

### Как работает
- Форк **не трогает** существующий DTLS-слой (`-no-dtls` описан в хелпе как «DO NOT USE» — автор сам считает его обязательным).
- При разработке STEALTH_MODE проводится сравнение DTLS-рукопожатия форка с эталонным VK-звонком через Wireshark: cipher suites, порядок extensions, версии должны совпадать.
- Если upstream изменит DTLS-параметры — отслеживать при мерже как приоритетное изменение.
- Цель: DTLS-рукопожатие форка неотличимо от оригинального клиента VK Calls.

---

## 5. Adaptive Channels (автомасштабирование каналов)

### Зачем
Сейчас количество каналов (`-n`) задаётся пользователем вручную. Слишком мало — низкая скорость. Слишком много — лишняя нагрузка на VK-инфраструктуру и повышенный риск детекции. Нужен баланс, выбираемый автоматически.

### Как работает
- При старте открывается минимальное число каналов (по умолчанию **2**).
- Каждые N секунд измеряется текущий throughput и утилизация буфера.
- Если буфер стабильно заполнен >70% — добавляется канал (до заданного максимума).
- Если буфер стабильно пуст <20% дольше M секунд — канал закрывается.
- Максимум каналов задаётся параметром `-n` (как сейчас), но теперь это **потолок**, а не фиксированное значение.
- В STEALTH_MODE приложение показывает пользователю текущее число активных каналов и приблизительную скорость: «Stealth: вкл — 4 канала, ~2.2 Мбит/с».
- Это снижает нагрузку на VK в idle и увеличивает её только когда реально нужно.

## 6. Rotation ссылок на уровне прокси

**Нужно для Android клиента, не для прокси как такового**

### Зачем
Одна TURN-сессия длиной 6–8+ часов нетипична для VK-звонка — реальные звонки короткие. Длинная сессия — потенциальный признак туннеля. Кроме того, ссылки могут «протухать» в любой момент, и плановая ротация снижает риск внезапного обрыва.

### Как работает
- Прокси хранит **очередь ссылок** (аналогично логике Telegram-бота из этого проекта).
- Ротация происходит в двух случаях:
  1. **Плановая** — каждые N часов (настраивается, по умолчанию ~2–3 часа) даже при живой ссылке.
  2. **Экстренная** — если текущая ссылка умерла (health check не прошёл).
- При ротации: новая ссылка проверяется перед активацией (health check, 2 попытки), старые каналы закрываются плавно (drain), новые открываются — без разрыва туннеля для пользователя.
- Мёртвые ссылки удаляются из очереди с логированием.
- Если очередь пуста — уведомление пользователю (в приложении) или алерт (в серверном режиме).
- **Резервный бэкенд**: если VK-ссылки недоступны, прокси может переключиться на Yandex Telemost (`-yandex-link`, уже поддерживается клиентом). Разные провайдеры TURN вряд ли заблокируют одновременно.

## Риски и митигации

| Риск | Описание | Митигация |
|------|----------|-----------|
| Снижение пропускной способности | Pacing ставит потолок на канал | Adaptive channels компенсируют масштабированием |
| Сложность отладки | Pacing-баг может убить весь туннель | Изолированный пакет `stealth/` с unit-тестами; тестовый стенд с `tc` для эмуляции плохого канала |
| Несовместимость после мержа | Upstream может изменить внутренний протокол | Версия протокола в рукопожатии с первого коммита; DTLS-слой не трогаем |
| Переполнение буфера | Данных больше чем влезает в слоты | Явное ограничение буфера + back-pressure на WireGuard-сторону |
| Нагрузка на VK при высоком n | 16 каналов × несколько клиентов | Adaptive channels держат n минимальным в idle |

## Структура нового кода

```
stealth/
├── stealth.go          # Основной middleware: определение интерфейса
├── padding.go          # Логика padding и wire-формат пакетов
├── pacing.go           # Таймер отправки, буферизация
├── dummy.go            # Генерация dummy/comfort-noise пакетов
├── adaptive.go         # Логика масштабирования каналов
├── rotation.go         # Очередь ссылок и логика ротации
└── stealth_test.go     # Unit-тесты без TURN
```

Переключение в `main.go`:
```go
if os.Getenv("STEALTH_MODE") == "true" {
    transport = stealth.NewTransport(baseTransport, stealth.DefaultConfig())
} else {
    transport = baseTransport
}
```
