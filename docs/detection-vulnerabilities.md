# Анализ уязвимостей детектирования VPN-трафика через TURN VK

**Перспектива**: DPI-система / цензор, задача — выявить и отличить srvk-turn-proxy от легитимных видеозвонков VK Calls.

Анализ упорядочен по уровню критичности для детектирования: от самых надёжных паттернов к менее значимым.

---

## КРИТИЧЕСКИЙ УРОВЕНЬ — надёжная детекция

### 1. Однонаправленный pacing (самая серьёзная проблема)

**Файл**: `stealth/pacer.go`

Pacing применяется **только на исходящем (outbound) направлении** каждой стороны. Входящие пакеты (`processInbound`, строка 281) декодируются и проксируются **без задержки и padding**:

```go
func (p *Pacer) processInbound(frame []byte, src net.Conn) error {
    flags, payload, err := p.framer.Decode(frame)
    if flags != FlagData { return nil }
    _, err = src.Write(payload)  // ← сразу в WG, без pacing
    return err
}
```

Каждая сторона (клиент и сервер) добавляет pacing **только** к тому, что отправляет в DTLS. Но **получатель не применяет pacing к доставке в WG** — просто пересылает. Это создаёт **асимметрию на стороне TURN-сервера**:

- **Client → TURN**: ритмичные пакеты 20/33ms
- **TURN → Client**: произвольный timing (диктуется WG/сервером, а сервер тоже pacing, но не синхронизирован с клиентом)

В реальном видеозвонке VK оба потока (audio/video) имеют **коррелированные интервалы** — оба участника генерируют пакеты примерно одновременно, есть echo cancellation, jitter buffer, и ARC (adaptive rate control). Здесь корреляция между потоками **полностью отсутствует** — это сильный статистический сигнал.

### 2. Отсутствие имитации сигнализации VK Calls

Легитимный видеозвонок VK начинается со **значительной сигнальной фазы**:

1. ICE connectivity checks (STUN Binding Requests/Responses)
2. DTLS handshake (как обычно)
3. Согласование SRTP через DTLS-SRTP (используя `use_srtp` extension)
4. RTP/RTCP мультиплексирование (RFC 5761)
5. RTCP Receiver Reports, Sender Reports, PLI/FIR для видео

srvk-turn-proxy пропускает **всё это**. После TURN allocation и DTLS handshake сразу начинается передача данных. DPI может отслеживать:

- **Отсутствие ICE checks** перед DTLS (STUN Binding Requests с атрибутами ICE-CONTROLLING/CONTROLLED)
- **Отсутствие `use_srtp` extension** в DTLS ClientHello — VK Calls обязательно согласовывает SRTP profiles
- **Отсутствие RTCP** — в легитимном звонке RTCP пакеты (~5 секундные интервалы) всегда присутствуют

### 3. Паттерн TURN allocations — массовый burst

**Файл**: `client/main.go:1175`

```go
t := time.Tick(200 * time.Millisecond)
```

Legacy режим создаёт **16 TURN allocations с интервалом 200ms** — суммарно за 3.2 секунды.

Stealth adaptive начинает с `stealth-min` (default 2) каналов, но **каждый канал делает отдельный TURN Allocate** с одними и теми же credentials. Реальный VK Calls клиент:

- Создаёт **1 allocation** (максимум 2 — audio + video relay candidate)
- Использует ICE для выбора лучшего пути, часто TURN не используется вообще (P2P preferred)

DPI видит: с одного IP, с одними credentials, **2-16 TURN Allocate запросов** за секунды — это аномалия.

### 4. Продолжительность сессии TURN

Легитимный видеозвонок VK длится **в среднем 5-15 минут**, редко более часа. srvk-turn-proxy держит TURN allocation **часами/днями** (пока запущен). DPI может:

- Отслеживать duration TURN-сессий
- Сессии > 2 часов — пометить как подозрительные
- Сессии > 6 часов — с высокой вероятностью не видеозвонок

### 5. Отсутствие второго участника звонка

VK Calls — это **двусторонний** звонок. TURN сервер VK видит:

- **Нашу сторону**: TURN allocation + data relay через CreatePermission на IP сервера
- **Вторую сторону**: должен быть другой VK-клиент, подключённый через те же сигнальные каналы

Но наш сервер (`server/main.go`) — это **не** VK-клиент. Он слушает на `0.0.0.0:56000` и принимает прямые DTLS-соединения. Для TURN сервера VK:

- `CreatePermission` идёт на наш сервер — IP, который **не является VK-клиентом**
- Этот IP не делал ICE connectivity check к TURN серверу
- Не было второго TURN allocation от "собеседника"

VK может тривиально выявить это на своей стороне (server-side), сопоставив: "allocation 1 отправляет данные на IP X, но IP X не участвует в calls.okcdn.ru API как второй peer".

## ВЫСОКИЙ УРОВЕНЬ — статистическая детекция

### 6. Распределение размеров пакетов слишком "чистое"

**Файл**: `stealth/padder.go:16-17`

```go
AudioProfile = SizeProfile{Min: 100, Max: 200}
VideoProfile = SizeProfile{Min: 800, Max: 1400}
```

Реальный WebRTC трафик VK Calls:
- **Opus audio**: 10-80 байт payload (20ms фреймы при разных bitrate: 6-64 kbps), с SRTP overhead → ~50-120 байт на wire
- **VP8/H.264 video**: крайне вариативные размеры — I-фреймы **фрагментированы на MTU** (≤1200 байт), P-фреймы часто 100-600 байт, иногда < 50 байт для skip-фреймов
- **RTCP**: 28-128 байт, периодические
- **DTLS-SRTP**: добавляет 12-16 байт SRTP overhead

В srvk-turn-proxy:
- Размеры **равномерно** распределены в [100, 200] и [800, 1400] с jitter ±5
- **Нет размеров < 100 байт** (а в реальном VK Calls их ~15-20%)
- **Нет размеров в "зазоре" 200-800** (а реальный VP8 генерирует пакеты 200-800 байт для P-фреймов)
- **Чёткая бимодальность** с пустым промежутком — это статистический маркер

DPI может построить гистограмму размеров пакетов для TURN-сессии и выявить отсутствие промежуточных размеров.

### 7. Слишком стабильный межпакетный интервал

**Файл**: `stealth/pacer.go:15-17`

```go
audioInterval = 20 * time.Millisecond
videoInterval = 33 * time.Millisecond
jitterRange   = 2 * time.Millisecond // ±2ms
```

Jitter ±2ms — это **слишком мало**. Реальный WebRTC jitter:

- Network jitter: 5-50ms типично
- Codec jitter: VP8 variable bitrate создаёт burst'ы (несколько пакетов подряд для одного фрейма, потом пауза)
- Jitter buffer на приёмнике выравнивает, но **на wire** видна дисперсия 10-100ms

У srvk-turn-proxy межпакетный интервал будет: `20ms ± 2ms` (video: `33ms ± 2ms`). Автокорреляция временных рядов покажет **чёткие пики** на этих частотах с **очень малой дисперсией** — характерный признак синтетического трафика.

### 8. Отсутствие burst-паттернов видеокодека

Реальный VP8/VP9/H.264:
- **I-фрейм** (keyframe): 15-100 КБ → фрагментируется на 10-80 пакетов, отправляемых **burst'ом** (микросекунды между ними)
- **P-фреймы**: 1-5 КБ → 1-4 пакета
- Паттерн: `...burst 50 pkts...gap 33ms...burst 3 pkts...gap 33ms...`

В srvk-turn-proxy: **строго 1 пакет каждые 33ms**. Никаких burst'ов. Это фундаментально отличается от любого видеокодека.

### 9. Dummy-трафик идентичен во всех состояниях

**Файл**: `stealth/pacer.go:186-193`

```go
default:
    targetSize := p.padder.TargetSize(0) // AudioProfile для dummy
    frame := p.framer.Encode(FlagDummy, nil, targetSize)
```

Когда нет реальных данных (VPN idle), все пакеты — dummy в AudioProfile (100-200 байт). Это значит:

- **100% idle**: поток из пакетов 100-200 байт каждые 20/33ms — нет видео-фреймов вообще
- **Активность**: появляются пакеты 800-1400 байт

Переход между "idle" и "активность" в VPN-туннеле **не коррелирует с видеозвонком**. В реальном звонке:
- Если человек молчит, audio comfort noise всё ещё ~20 байт
- Если камера включена, видеопоток постоянный
- **Нет резкого перехода "нет видео → есть видео"** без явного действия пользователя (включение камеры)

Здесь видеоразмерные пакеты появляются при обычном веб-серфинге через VPN — DPI увидит паттерн "video включается/выключается десятки раз в минуту", что не свойственно звонку.

### 10. Содержимое TURN ChannelData — не SRTP

Внутри TURN ChannelData (RFC 5766) легитимный VK Calls передаёт **SRTP пакеты**. SRTP имеет характерную структуру:

```
[V=2][P][X][CC][M][PT][Seq][Timestamp][SSRC][...payload...][auth_tag]
```

- Первые 2 бита = `10` (RTP version 2)
- PT (payload type): 111 для Opus, 96-127 для видеокодеков
- Sequence number инкрементируется
- Timestamp предсказуемо растёт

В srvk-turn-proxy внутри TURN ChannelData идёт stealth-фрейм:

```
[0xA1/0xA2][payload_len BE][WireGuard packet][random padding]
```

Первый байт **0xA1** — это не валидный RTP. Если TURN сервер VK анализирует содержимое relay'ных пакетов (что технически возможно, хотя обычно не делается), фрейм **мгновенно** выдаёт не-RTP трафик.

Даже без deep inspection: WireGuard пакеты внутри начинаются с `0x01-0x04`, а после stealth Encode — с `0xA1`. DPI на TURN сервере может проверить, что relay'ные данные не являются SRTP — 1 проверка, 100% детекция.

## СРЕДНИЙ УРОВЕНЬ — требуют более глубокого анализа

### 11. DTLS ClientHello fingerprint

Единственный cipher suite `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256` — это **допустимо** для WebRTC (Chrome/Firefox поддерживают), но:

- Реальный браузер в ClientHello предлагает **несколько** cipher suites (обычно 4-8)
- Pion DTLS формирует ClientHello **отлично** от браузерного — другой порядок extensions, другие supported groups, отсутствие signature_algorithms, нет ALPN
- `ExtendedMasterSecret: require` — специфичная комбинация

JA3-подобный fingerprint для DTLS (JA3S адаптация) выявит: "это pion/dtls v3, не Chrome WebRTC".

### 12. Connection ID (CID) — маркер pion/dtls

**Client**: `OnlySendCIDGenerator()` — клиент **только отправляет** CID, не запрашивает
**Server**: `RandomCIDGenerator(8)` — 8-байтные CID

В браузерном WebRTC (Chromium) CID **не используется** — это расширение поддерживается не всеми. Наличие CID в DTLS-сессии через VK TURN сервер — **аномалия**.

### 13. Self-signed сертификаты без SRTP

`selfsign.GenerateSelfSigned()` генерирует сертификат с **одним** ключом ECDSA P-256. В WebRTC это нормально (SRTP keys извлекаются через DTLS-SRTP handshake). Но:

- Отсутствие `use_srtp` extension в ClientHello
- Нет `srtp_mki` согласования
- Handshake не содержит SRTP Key Material Export

Это видно на уровне DTLS handshake, который **не зашифрован** (ClientHello/ServerHello в открытом виде).

### 14. DNS-резолвинг VK API через нестандартные резолверы

**Файл**: `client/main.go:1123-1127`

```go
dnsdialer.WithResolvers("77.88.8.8:53", "77.88.8.1:53", "8.8.8.8:53", "8.8.4.4:53", "1.1.1.1:53"),
```

Клиент резолвит `login.vk.ru`, `api.vk.ru`, `calls.okcdn.ru` через **Yandex DNS / Google DNS / Cloudflare** вместо системного резолвера. ISP видит:

1. DNS-запросы к `login.vk.ru` через 8.8.8.8 (нетипично для обычного пользователя VK)
2. Затем TURN-трафик на IP из ответа VK API

### 15. API-вызовы без реального клиента VK

Последовательность `get_anonym_token → getAnonymousToken → auth.anonymLogin → vchat.joinConversationByLink`:

- `isVideo=false` — всегда audio-only
- `name=123` — имя участника всегда "123"
- `protocolVersion=5` — фиксированная версия
- User-Agent: `Firefox/144.0` — может быть устаревшим

VK server-side может:
- Отслеживать аномальные имена ("123", "Гость")
- Корреляция: join по ссылке → нет реального WebRTC сигналинга (не подключается к calls-ws.vk.com)
- Один и тот же link используется многократно (обычно link одноразовый)

## НИЗКИЙ УРОВЕНЬ — требуют целенаправленного анализа

### 16. Mixed mode — фиксированная граница 200 байт

**Файл**: `stealth/pacer.go:326`

```go
if n <= 200 {
    select { case p.audioCh <- pkt: }
} else {
    select { case p.videoCh <- pkt: }
}
```

WireGuard пакеты делятся на audio/video каналы по размеру 200 байт. Это не имеет смысла с точки зрения WebRTC (где разделение идёт по RTP payload type). Но для внешнего наблюдателя это менее заметно.

### 17. Адаптивное масштабирование — предсказуемый паттерн

`adaptiveLoop` каждые 5 секунд проверяет утилизацию. При `>70%` три тика подряд → +1 канал. Это создаёт **паттерн**: новый TURN Allocate запрос через ~15 секунд после роста нагрузки — предсказуемая реакция, не свойственная обычным звонкам.

### 18. Version info в первом пакете

**Файл**: `stealth/framer.go:138-144`

Первый пакет содержит `[0xA1][payload_len][version=1][pacing_mode][0x00][0x00][...data...]`. Если DPI имеет доступ к содержимому DTLS (что маловероятно при AES-128-GCM), это уникальная сигнатура. Но внутри DTLS это нерелевантно.

## Заключение

**Stealth-mode** существенно улучшает ситуацию по сравнению с main: padding, pacing и dummy traffic закрывают самые простые методы детекции (анализ размеров "голых" WireGuard пакетов, молчание при idle).

Однако **фундаментальные проблемы** остаются:

1. **Протокольная неполнота**: отсутствие ICE, SRTP, RTCP делает трафик непохожим на реальный WebRTC-звонок при глубоком анализе
2. **Server-side детекция VK**: VK имеет полную видимость — credentials, количество allocations, отсутствие второго участника, содержимое relay. При желании VK может блокировать 100% туннелей
3. **Статистическая модель**: синтетический pacing (ровные интервалы без burst'ов) + бимодальные размеры без промежутков → выявляется ML-классификатором на обучающей выборке из 100-200 сессий

**Самое слабое звено** — не DPI, а **сторона VK**. Если VK решит бороться с этим, достаточно проверять: "есть ли второй легитимный participant в звонке, на который указывает relay allocation?" — и все туннели заблокированы.
